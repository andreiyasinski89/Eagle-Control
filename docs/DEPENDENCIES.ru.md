## 2. Порядок работ

Каждый этап: отдельная ветка, все проверки зелёные, затем слияние и наблюдение за сайтом. Между этапами не меньше суток на проде.

### Этап 0. Подготовка (полчаса)
- Убедиться, что на `main` всё зелёное: `npx tsc --noEmit`, `npx eslint .`, `npx vitest run`, `npx next build`, браузерные сценарии `npx playwright test` (теперь работают без Docker благодаря `scripts/e2e-mailbox.mjs`).
- Записать эталон: 1333 теста, время сборки, размеры страниц из `next build`.
- Закрепить версию Node в `package.json` (`"engines": {"node": ">=22"}`), чтобы Vercel и локальная машина не расходились.

### Этап 1. Мелкие и «безопасные» обновления (1–2 часа, риск низкий)
Патчи и минорные версии, ломать нечему:
`next` 15.5.29, `eslint-config-next` 15.5.29, `@tanstack/react-query` 5.105, `@tiptap/*` 3.32.2, `@xyflow/react` 12.12.1, `lucide-react` 1.68, `resend` 6.37, `inngest` 4.26.2, `tailwindcss` и `@tailwindcss/postcss` 4.3.4, `postcss` 8.5.32, `@aws-sdk/*` 3.1161, `read-excel-file` 9.3.14, `vitest` и `@vitest/coverage-v8` 5.1, `@types/node` 26.6.6, `@electric-sql/pglite` 0.5.15.

Особое внимание: `lucide-react` (иконки переименовывают, проверит `tsc`) и `vitest` (минор, возможны новые предупреждения).

### Этап 2. `nodemailer` 8 → 10 (2 часа, риск низкий)
Закрывает обе уязвимости nodemailer. Мы используем только `createTransport(...).sendMail(...)`, в `src/server/mail/index.ts`.
- Проблема: `next-auth` указывает у себя `nodemailer ^7 || ^8`. Решение: в `package.json` добавить `"overrides": {"nodemailer": "^10.3.1"}`. Это безопасно: встроенный почтовый провайдер `next-auth` мы не подключаем, письма отправляет наш код.
- Проверить: тесты `mail-errors`, `signin`, `platform-setup`; кнопка «Проверить» в `/admin/setup` на проде (приходит пробное письмо); вход по письму целиком (браузерный сценарий `onboarding`).
- Откат: вернуть `^8.0.11`, убрать `overrides`.

### Этап 3. `zod` 3 → 4 (1–2 дня, риск средний)
Zod используется в **90 файлах** (все входы API, окружение, формы). Самая трудоёмкая из «безопасных» миграций.
- Инструмент: официальный перенос `npx zod-v3-to-v4` (или `@zod/codemod`), затем ручная проверка.
- Что известно как ломающее: сообщения об ошибках (`message` теперь `error`), `z.record()` требует схему ключа, `.merge()` и `.strict()` заменены, `z.string().email()` и подобные становятся `z.email()`, `.default()` и `.optional()` иначе работают с `undefined`, у `ZodError` другая форма `issues`. У нас ответ API содержит `issues`: **проверить, что клиент (формы) читает их так же**.
- Порядок: сначала сменить версию и прогнать `tsc` (покажет всё, что сломалось в типах), потом тесты. Особенно внимательно: `src/lib/env.ts` (разбор окружения при запуске: ошибка здесь роняет весь сайт), `src/server/http/handler.ts`, схемы публичного API (`src/server/public-api`) и MCP.
- `inngest` 4.26 принимает оба zod (`^3.25 || ^4`), блокировки нет.
- Откат: возврат на `^3.25.76` и `git revert` кодмода.

### Этап 4. `next` 15 → 16 (1–2 дня, риск средний)
Закрывает вложенный `postcss`. `next-auth` (beta.32), `next-intl` 4.14 и `eslint-config-next` 16 уже совместимы с Next 16. React 19 у нас уже есть, Node 24 подходит.
- Известные изменения Next 16: файл `middleware.ts` переименовывается в `proxy.ts` (`src/middleware.ts` с `next-intl`), сборка по умолчанию через Turbopack, параметры страниц уже асинхронные (мы так и пишем), поменялись некоторые настройки в `next.config.ts` (`redirects`, заголовки остаются).
- Проверить: `next build` целиком; страницы входа (Auth.js + наши обёртки из `src/server/auth/`); `/ua/...` и `/uk/...` (перенаправление, добавленное 4 ноября); service worker и PWA; заголовок CSP; `robots.txt`; все браузерные сценарии; на проде открыть все разделы кабинета (сценарий проверки из этого ревью).
- Откат: вернуть `^15.5` и старое имя `middleware.ts`.

### Этап 5. `prisma` 6 → 7 (2–3 дня, риск выше среднего)
Закрывает `deepmerge-ts` (в утилите). Самый рискованный этап: Prisma 7 меняет способ подключения к базе.
- Что меняется: обязательные «адаптеры драйверов» (`@prisma/adapter-pg` или Neon-адаптер), конфигурация переезжает в `prisma.config.ts` (сейчас она в `package.json#prisma`, и сама Prisma об этом предупреждает), новый генератор `prisma-client`, пути импорта клиента.
- Для разработки: `pglite-prisma-adapter` 0.7.2 уже требует Prisma 7.
- Риск для нас: наш слой повторов запросов (`src/server/db-retry.ts`) и подсчёт времени запросов (`src/server/db.ts`) привязаны к `$extends`/событиям клиента, их надо перенести; тесты на PGlite (`src/tests/integration/pg.ts`) пересобрать под адаптеры; пул соединений Neon (`connection_limit=…`) задаётся иначе.
- Делать только после этапов 1–4, на отдельной ветке и **сначала на копии базы** (Neon умеет ветвление).
- Откат: вернуть `^6.19.3` и прежний генератор; миграции базы при этом не меняются.

## 4. Как не накапливать долг
1. Включить Dependabot (или Renovate) на еженедельные пулл-реквесты **только для патчей и минорных версий**, мажорные вручную по этому плану. Файл `.github/dependabot.yml` на 15 строк.
2. В проверках на GitHub (CI) добавить `npm audit --omit=dev --audit-level=high` как **предупреждение**, не блокировку: пока есть этапы 3–5, он будет красным, и это ожидаемо.
3. Раз в месяц: `npm outdated` и пересмотр этого плана.
