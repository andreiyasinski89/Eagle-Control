# Decisions

| # | Decision | Why |
|---|---|---|
| 1 | Single Next.js app, not a monorepo | Simplest for MVP; module boundaries by folder. |
| 2 | Realtime: **Liveblocks** (Phase 4) | Presence/cursors out of the box, DB-agnostic. Supabase Realtime would push us to RLS, which doesn't fit Prisma + Auth.js. |
| 3 | Queue: **Inngest** (Phase 4+) | Works on Vercel serverless without Redis or a long-lived worker. |
| 4 | Auto-layout: dagre first, elkjs if perf demands (Phase 2) | Dagre is enough for trees. |
| 5 | `Node.position` is a `Float` (insert at midpoint) | Moving a node touches one row; rebalance occasionally. |
| 6 | CRM entities are 1:1 extension tables keyed by `nodeId` | One tree, typed columns for filters and reports. |
| 7 | Storage: Cloudflare R2 (EU jurisdiction) in prod, MinIO locally | S3-compatible, GDPR-friendly. |
| 8 | Authorization in `server/policies` (pure functions), checked in every route; non-members get 404, not 403 | No RLS (no Supabase); avoids leaking workspace ids. |
| 9 | Sign-in: magic link + Google, no passwords | Smaller attack surface. Default chosen when the question was left open. |
| 10 | Mail: Resend when `RESEND_API_KEY` set, SMTP (Mailpit) otherwise | Default chosen when left open. |
| 11 | Package manager: **npm** (not pnpm) | pnpm was not installed in the build environment; no feature depends on it. Switching later is trivial. |
| 12 | Auth.js database sessions via Prisma adapter | Revocable sessions; auth is checked in layouts/handlers, not middleware (middleware only does i18n). |
| 13 | Invitation tokens stored as SHA-256 hash; re-inviting revokes the previous link; accept requires the signed-in email to match | A leaked DB can't be used to join; links can't be forwarded to another account. |
| 14 | Free user limit counts members **plus pending invitations** | Prevents exceeding the cap by sending many invites. |
| 15 | Invitable roles: ADMIN, MEMBER, GUEST, CLIENT; OWNER can't be granted (no ownership transfer yet) | Keeps "at least one owner" trivially safe; last owner can't be demoted or removed. |
| 16 | `crmAccess` lives on `Membership`; owners/admins always see CRM | Matches "not everyone should see deal amounts". |
| 17 | New workspace gets a default "Sales" pipeline (7 stages) and lost-reason dictionary | Needed by Phase 3, and the free plan allows exactly one pipeline. |
| 18 | `ActivityLog` has no FK to `Node` | Audit trail must survive node deletion. |
| 19 | Extra tables beyond the spec: Account/Session/VerificationToken, Invitation, ProjectMember, LostReason, Notification, LeadForm, Integration, AiUsage, Subscription, ConsentRecord | Implied by the spec (auth, guest access, lost-reason dictionary, GDPR consent, limits) but not listed. |
| 20 | Raw SQL in the first migration: CHECK on progress/probability, "override needs note", partial index on active nodes | Prisma can't express these. |
| 21 | Tailwind v4 + hand-written shadcn-style components | The shadcn CLI needs an interactive setup; swap in later without changing call sites. |
| 22 | `Node.rootId` (denormalised project id; null on the project itself) added in migration 0002 | One indexed query loads a project tree, and access checks for guests/clients need no recursive CTE. |
| 23 | Health is recomputed on read (`GET /projects/:id/tree`, `GET /nodes/:id`) and persisted on every write | It depends on "today", so stored values go stale overnight; persisted values stay useful for SQL filters. A nightly refresh job comes with Inngest in Phase 4. |
| 24 | Whole project tree is returned flat; collapsed branches are simply not rendered | Parent progress/health need every descendant anyway. True lazy loading was dropped from the plan. |
| 25 | Own left-to-right tidy-tree layout (`modules/nodes/layout.ts`) instead of dagre/elkjs; dagre removed | Generic graph layouts do not guarantee sibling order; this is O(n), deterministic and unit-tested. Runs on the main thread (2000 nodes < 200 ms), no worker needed so far. |
| 26 | Delete = archive the subtree with one shared timestamp; restore brings back exactly what was archived together | Makes undo exact. Permanent deletion is not exposed. |
| 27 | Undo/redo is client-side: each action records inverse API ops, replayed through `POST /nodes/batch` (atomic) | 50 steps, survives nothing across reloads by design. |
| 28 | Progress rules: weight = own estimation, containers sum their descendants'; missing weights fall back to the mean of known siblings, else 1; documents, events and cancelled work are ignored; AUTO tasks derive from subtasks; derived progress cannot be typed in (`409 progress_derived`) | Matches the spec; fallback rule was ambiguous. |
| 29 | Health: lag of exactly 30 points is yellow (red is > 30); the "last 20% of time and < 70%" rule is implied by the lag rule whenever both dates exist; dates compare by UTC calendar day; "no assignee" only applies to tasks/subtasks | Spec boundaries were ambiguous. |
| 30 | Guests may edit nodes in projects they were added to; clients are read-only + comments | Spec says guests get access to invited projects. |
| 31 | Comments are stored as a Tiptap-shaped document; the composer is a plain textarea with a hand-written @autocomplete that inserts real mention nodes | The Tiptap Mention extension needs a popup library; ids travel with the text, so notifications are exact. |
| 32 | Integration tests run real migrations on PGlite (`pglite-prisma-adapter@0.6.1`, newer versions need Prisma 7) | Verifies SQL, constraints and transactions without Docker. |
| 33 | Built-in project templates live in code (`modules/nodes/templates.ts`); `ProjectTemplate` rows are for workspace-defined templates (Phase 3) | No dependence on a seeded DB. |
| 34 | CRM tree: a company is the root, its contacts and deals are children (`parentId` = `rootId` = company); contacts and deals without a company are stand-alone roots. Projects hang off deals by `NodeLink(DEAL_PROJECT)` and `project.data.{dealId,companyId}`, never by `parentId` | The project must not depend on the CRM. The Client Map draws the link dashed. |
| 35 | Company, contact and deal nodes are invisible without `crm:read` (404, not 403) and refuse project-tree operations (`422 use_crm_endpoint`); generic comments, files, tags and history work on them | Amounts and personal data stay behind the CRM flag; the generic node endpoints are reused instead of duplicated. |
| 36 | Winning a deal and creating its project are two calls; the dialog chains them | A Free-plan project limit can never block a sale. |
| 37 | Project dates from a deal: start = win date (or the date typed), due = start + template length (60 days by default); template nodes carry `offsetDays` / `durationDays` | The sales close date is not a delivery deadline; undated sprints would make health meaningless. |
| 38 | Money is never converted: column and company totals are per currency | No FX source of truth; mixed sums would mislead. |
| 39 | Deal health: red after 14 idle days, 30 days in one stage, or a passed close date; yellow without a next step (or an overdue one) or after 7 idle days. A stage move or any completed activity resets the idle clock | Defaults of the spec's "N days"; constants live in `crm/common.ts`, workspace settings can override them later. |
| 40 | "No touch", "stuck deal" and "close date passed" reminders are computed when My Day is read; e-mail reminders need the queue from Phase 4 | No background worker exists yet. |
| 41 | Duplicates: e-mail (lower-cased) and the last 9 phone digits for contacts; domain, normalised name (no legal form, diacritics) and tax ID for companies. Creating warns with `409 duplicate_contact/company` unless `allowDuplicate`. Merge deletes the absorbed records after moving their history and never inherits consent | Deleting leaves no stray copy of personal data behind. |
| 42 | CSV import is stateless two-step (preview, then commit with the same file), 5 MB / 5,000 rows, atomic, BOM/UTF-8 first then Windows-1251/1250; exports neutralise spreadsheet formulas but keep phone numbers and @handles readable | No staging table full of personal data; larger files need the Phase 4 queue. |
| 43 | GDPR erase is a hard delete (contact, activities, consent records, lead submissions, history), owner/admin only, `{"confirm":"ERASE"}`, with a PII-free audit entry; export is a JSON dump | Chosen over anonymisation as proposed in the phase plan. |
| 44 | Lead intake: contact matched by e-mail/phone, company by domain or name; a repeat inquiry within 14 days joins the open deal instead of creating another; honeypot is answered with success but stored as rejected; `Idempotency-Key` makes retries safe; browsers from sites outside `allowedOrigins` get 403; client IPs are stored only as a truncated hash | Public endpoints are the main attack surface. No CAPTCHA (needs a provider key). |
| 45 | The webhook token is shown once and stored as a SHA-256 hash; rotating revokes the old one. One inbound webhook per workspace | Matches the one-row-per-kind `Integration` table. |
| 46 | Client Map and the pipeline-as-map use a separate read-only `TreeMap` (same layout and health colours) instead of generalising the editable project canvas | Refactoring the working project map was the riskiest part of the plan; the CRM maps do not need editing. Projects open in their own map from the Client Map. |
| 47 | The hosted lead form lives under its own root layout `(public)/f/[key]`; only `/f/*` may be framed (`frame-ancestors *`), everything else keeps `X-Frame-Options: DENY` | The form is meant to be embedded; embedding cannot be restricted per form without edge lookups, so `allowedOrigins` restricts who may post. |
| 48 | Metrics come from append-only history tables (`NodeStatusEvent`, `DealStageEvent`), written in the same transaction as the change; migration 0004 backfills them from `Node` and `ActivityLog` | Burndown, CFD, cycle time and the funnel need the past, not the current state. Backfilled creation events are assumed TODO. |
| 49 | Notifications go through an outbox: `notify()` stores the row plus `pendingChannels`, `deliverPending()` sends and clears them; `(userId, dedupeKey)` is unique | Delivery can retry after a crash without duplicates, and the same producer works inline or from a queue. |
| 50 | Background work is plain task functions behind `JOBS_MODE=inline|inngest`; Inngest functions only wrap them (cron + events) | Everything is testable without Inngest, and self-hosters without it still get delivery on request. Inngest cloud was not run here. |
| 51 | Integration secrets are encrypted with AES-256-GCM (`SECRETS_KEY`, `v1.<iv>.<tag>.<ct>`); a missing or wrong key fails loudly | Tokens for Google, Slack and Telegram must not sit in the database in clear text. |
| 52 | Time entries are whole minutes per day; one running timer per person, starting another logs the first; <30 s logs nothing, a forgotten timer is capped at 24 h, a day cannot exceed 24 h; no entries for the future | Keeps typos and forgotten timers from polluting reports. |
| 53 | Hourly rates live on the membership (owners/admins edit and see them); a project's `data.hourlyRate` overrides the person's rate; only billable minutes earn money; amounts are rounded once per group; members see hours but `amount: null` | Rates are payroll-sensitive; billing needs a per-project override. |
| 54 | A client's time report covers every project linked to its deals (`DEAL_PROJECT`), period at most one year, no currency conversion (one currency per report) | Same rule as decision 38; the link already ties delivery to the client. |
| 55 | Views (map, board, list, calendar, timeline) read the same Zustand store and are picked by `?view=` next to `?node=`; no second data layer | Edits stay optimistic and consistent between views; every view is shareable as a link. |
| 56 | Board and calendar drags use native HTML5 drag and drop plus a keyboard/touch alternative (status select on cards); the timeline uses pointer events and arrow keys; no new dependency | Small bundle; the alternative also makes the actions testable without drag simulation. |
| 57 | The workspace calendar is one endpoint merging task/sprint/epic due dates, events, CRM activities and deals' next step / expected close; guests and clients see only their projects, CRM items need `crm:read`; window capped at ~2 months | One query per page view instead of one per source; permissions stay in one place. |
| 58 | Realtime events are invalidation hints (`tree.changed`, `comment.added`, `board.changed`, `notification`) with no content; receivers re-read through the authorised API. Presence (selection, editing, pointer) is the only state, kept in memory and expiring after 45 s | A stream can never reveal more than the API; no second source of truth to keep consistent. |
| 59 | Realtime transport is SSE with an in-process bus (`REALTIME_PROVIDER=sse`); other values fail loudly. Several instances need a shared backplane; Liveblocks is not built | Works with no extra service and is fully testable here; honest about its single-instance limit rather than shipping an adapter that could not be tried. |
| 60 | Remote refresh is debounced and waits while any local write is in flight; the node being edited keeps the local copy; drawer queries refresh only when no drawer field has focus | Prevents a remote update from overwriting or resetting what a person is typing. |
| 61 | Writers announce after commit where they own the transaction (`transact`); others announce 250 ms later from inside it | Receivers re-read, so they must find the committed rows; the delay is simpler than a commit hook for every service. |
| 62 | All integrations are gated by the workspace plan on every entry point, not only in the UI; the Telegram bot answers a workspace that dropped to Free with an error | A downgrade must stop the integrations, not just hide the page. |
| 63 | OAuth state is an HMAC-signed, 10-minute payload (person, workspace, purpose) and the callback must be opened by that same signed-in person | Stops forged callbacks and login CSRF; the callback never trusts query parameters alone. |
| 64 | Google Calendar: events are pushed to the creator's calendar with attendees invited by e-mail; the Google event id is derived from the node id and a duplicate create (409) becomes an update; pull uses a sync token (restarted on 410), skips our own etags and resolves conflicts by last write (local wins if the node changed after the last sync); only events created here are two-way | Idempotent across requests and servers, and avoids importing a whole personal calendar. Push channels need HTTPS, so a 10-minute poll is the fallback. |
| 65 | Slack: bot-token install per workspace, one channel per event kind, direct messages matched by e-mail; announcements are best effort and sent after the sale, sprint or health change is committed | A Slack outage must never fail the thing being announced. |
| 66 | Telegram: one bot for the installation; a person links a chat with a one-time code (15 minutes, stored hashed); commands act as that person; groups are ignored; the webhook is accepted only with the secret token | The bot must not become a way to act as someone else. |
| 67 | Slack and Telegram notifications go through the same outbox as e-mail; a person without a linked account is skipped, not retried | One retry policy; no endless retries for people who never connected. |
| 68 | Reports and metrics are Pro features; clients never see Agile metrics; the CRM report CSV needs the export right (today equal to CRM read) | Matches the plan table; the export check stays so the two rights can diverge. |
| 69 | The plan changes only from Stripe webhooks (event id recorded for idempotency, removed again if handling fails; an older snapshot never overwrites a newer one); the page after Checkout only waits and polls | A return URL can be opened by anyone and the redirect can arrive before the payment is final. |
| 70 | A failed payment keeps Pro for 7 days (grace counted from the first failure), then Free; a daily job enforces it even if Stripe is still retrying. Downgrades never delete data, they only apply limits to new items | Matches the promise made on the billing page; losing a customer's work over a failed card is not acceptable. |
| 71 | Public API tokens are personal: they act as their owner, inside one workspace, only while the owner is still a member (not a guest or client) and the workspace is on a plan with the API. Only a SHA-256 hash is stored | No separate permission system to keep in sync; revoking access to a person revokes their tokens. |
| 72 | The public API is one registry of endpoints (method, path, schemas, scope, handler); the dispatcher and the OpenAPI document are both built from it. Every id in a path is checked against the token's workspace before a service is called | Docs cannot drift from behaviour; a person in two workspaces cannot use a token from one to reach the other. |
| 73 | Outgoing webhooks go through an outbox with backoff (1 min, 5 min, 30 min, 2 h, 12 h), https only, no redirects, addresses checked at save and at send; project changes are coalesced per project | Receivers can be slow or down; a webhook must never be a way to probe our network. |
| 74 | Clients are shut out of the workspace app and API by policy (no `workspace:read`, no `comment:write`); the portal service is their only way in and answers 404 for anything not shared | One rule that cannot be forgotten in a new endpoint, instead of a client check in every service. |
| 75 | Sharing is per node (`visibleToClient`), per comment and per file; a node under a hidden parent is shown under its nearest shared ancestor; descriptions, assignees, estimates, time and internal comments are never part of a portal response | Teams share deliberately; the safe default for anything new is private. |
| 76 | Approvals: staff request on a shared node, one pending request per node, only a client can answer (owners previewing cannot), answers are final and a new request starts a new round; the answer is decided with a conditional update so two clicks cannot both win | An approval is evidence; it must be unambiguous. |
| 77 | AI output is always a draft. Subtask suggestions are validated JSON and are created only after a person picks them; the client update is built from shared nodes only; workspace text is wrapped as data and the system prompt forbids following it | Prompt injection through titles or comments must not be able to change anything or leak internal facts to clients. |
| 78 | AI usage records counts only (never prompts or answers); the allowance is per workspace per UTC month, checked before the call, with notices to owners at 80% and 100% | Privacy by default, and a predictable bill. |
| 79 | The caller's address is the entry our own proxy appended to `X-Forwarded-For` (`TRUSTED_PROXY_HOPS`), never the first entry | The first entry is client-controlled: trusting it made every rate limit optional. |
| 80 | Request bodies are read through a limiter that stops at a size cap regardless of Content-Length (1 MB default; 64 KB for the public lead form) | Chunked bodies and lying headers must not buffer unbounded memory; also mitigates the zod collection advisory. |
| 81 | Sign-in is rate limited per caller address and per mailbox, ahead of Auth.js | E-mail sending is the one unauthenticated action with a cost and a victim. |
| 82 | Production sends HSTS and a baseline CSP (inline scripts allowed; other origins only for storage uploads); the policy is production-only | Next.js needs inline scripts, but code loading and data exfiltration to other origins can still be blocked; development tooling needs eval. |
| 83 | Scheduled jobs can be triggered over HTTP with a bearer secret when Inngest is not used; the endpoint is off unless `CRON_SECRET` is set | Self-hosters otherwise have no way to run delivery, reminders and plan expiry. |
| 84 | A test inventories every API route and fails on any that is neither session-wrapped nor on a reviewed list with its own protection | The most likely security regression is a new endpoint that forgot authentication. |
| 85 | Erasing an account keeps the `User` row as an anonymous tombstone (name "Deleted user", address `deleted-<id>@deleted.invalid`) instead of deleting it; credentials and personal records are deleted | Tasks, comments, time entries and history keep their structure and every foreign key stays valid, while nothing identifies the person; the same e-mail can be registered again. |
| 86 | Workspaces where the person is the only owner and no other team member exists are deleted with the account (files and Stripe subscription first); where team members remain, the person must hand over ownership before deletion proceeds, and this is checked again when the job runs | No workspace is left without an owner, and no subscription keeps billing for deleted data. |
| 87 | Export and deletion need an e-mailed one-time code; deletion also needs the exact e-mail typed and waits a grace period (default 7 days) in which it can be cancelled | Re-authentication that a stolen session cannot satisfy, and protection against regret. |
| 88 | Time entries and CRM activities stay (anonymised); comments stay unless the person asks to have their text replaced with "[removed]" (which keeps the thread readable); their uploads are deleted only on that request | Billing records and other people's context must survive; the person decides about their own words. |
| 89 | Account events (requested, cancelled, blocked, deleted, exported, ownership transferred) are stored without a foreign key and without personal data | Evidence that a request was honoured must outlive the account. |
| 90 | A public demo is a deployment with `DEMO_MODE=true`: the sign-in page gets an "Open the demo" button (POST `/api/demo/login`) that signs anyone in as the demo owner of a shared sample workspace; the route is a 404 otherwise | Showing the product by link needs no mail service, accounts or tokens, and the switch cannot be on by accident (default off, documented as never for real use). |
| 91 | The demo workspace is built on the first visit and rebuilt by a daily job (`demo/reset`, Vercel Cron); the demo accounts cannot be exported or deleted | Visitors can change anything, so the shared data is thrown away every day; the demo addresses receive no mail, so those flows would only fail. |
| 92 | The hourly grid shows times in UTC, like the rest of the calendar (days, "today" and the current-time line included) | Changing the time zone of the calendar means changing how days are bucketed in the API and in every view; one consistent basis for now, a per-user time zone is a separate piece of work. |
| 93 | Pro without Stripe is a list of administrator addresses (`PRO_OWNER_EMAILS`) that puts workspaces they own on the Pro plan in the database; it only raises plans and never touches workspaces that have a subscription | Every feature check already reads the stored plan, so nothing else changes; Stripe stays the only authority for customers, and removing someone from the list cannot take a paid plan away by accident. |
| 94 | The e-mailed sign-in link goes to a confirmation page and the one-time link is used by a button (POST) | Mail scanners and link previews fetch every link in a message; a link that signs in on GET is burnt before the person clicks. |
| 95 | Daily sign-in limits live in the database as salted hashes (per caller address, per mailbox, per installation) next to the existing in-memory per-minute limits | The in-memory limits do not hold across serverless instances; the total protects the sender's own quota (Gmail suspends accounts that exceed it) and a stranger's mailbox from floods. |
| 96 | Agreeing to the terms is enforced on the server and recorded as the date of the first sign-in; the legal pages are drafts that say so | A checkbox only in the browser proves nothing; the texts need a lawyer, but the mechanism and the operator's identity are in place. |
| 97 | Until a domain exists, e-mail goes through SMTP with a login (Gmail app password) rather than Resend | Resend without a verified domain only delivers to its owner; Gmail delivers to anyone within a daily quota. |
| 98 | The Telegram webhook is registered by an owner/admin button instead of a manual command, and the integrations card asks Telegram where the bot's messages go | The one-time `curl` with the bot token was the step most likely to be skipped or leak the token; the status shows a misregistered or failing bot. |
| 99 | Leads from e-mail are read by a script in the owner's own Google account (Apps Script) that posts to the existing lead webhook, not by the server reading mailboxes | The server never holds Gmail access or mail content; no domain or inbound-mail provider is needed, and the webhook's idempotency and contact/deal reuse already prevent duplicates. |
| 100 | The look comes from the community theme Violet Dusk (21st.dev), applied as colour tokens and corner radii on our own components; no paid 21st.dev component code is copied in | A theme is free CSS tokens and keeps one design language; copying third-party component code means its licence, its dependencies and its bugs. |
| 101 | The typeface is Inter, not the theme's Plus Jakarta Sans | The interface is English, Polish and Russian; Inter has the Latin Extended and Cyrillic glyphs, and the theme lists it as the fallback anyway. |
| 102 | Workspace switching, the account menu and sign-out moved from the top bar into the sidebar; Ctrl+K opens a command palette over pages, projects and workspaces | The top bar was crowded with rarely used controls; jumping by keyboard is how people move around a tool like this. |
| 103 | A map that would need a zoom below 55% to fit opens at 55% with the root at the left edge, not zoomed out to fit | At the fit zoom the first thing people saw was dots; readable cards from the root outward show the product at once, and the fit button is one click away. |
| 104 | The Claude connection is an MCP server at `/api/mcp` that calls the public API's own dispatcher for every tool, instead of talking to the services directly | Token, plan, scope, membership, workspace boundary, rate limit, idempotency and audit are enforced in one place already; a second path would be a second place to get them wrong. The registry builds each tool's input schema from the endpoint's Zod schema, so tools and REST cannot drift. |
| 105 | Claude signs in with OAuth 2.1 (dynamic client registration, authorization code with PKCE S256 only, public clients, access tokens of one hour, refresh tokens that rotate); the access token is an ordinary API token tied to a grant | "Add custom connector" in Claude takes only an address and needs this flow. Reusing API tokens means nothing new can bypass the existing checks, and revoking a grant revokes its tokens. |
| 106 | A replayed refresh token closes the whole grant | A used token that shows up again is a retry bug or a stolen copy; ending the connection (the person reconnects in one click) is safer than guessing which. |
| 107 | Only a Pro workspace where the person is a member (not a guest or client) can be connected, and the person picks the workspace and read-only or read-and-write on the consent page | The connection acts as the person, so it must never reach more than they could, and a read-only choice removes every changing tool from what Claude is offered. |
| 108 | Anyone may register a client, so the consent page shows where the person will be sent back to and warns when it is not an Anthropic or local address | Open registration is how MCP clients introduce themselves; an app can call itself "Claude", but it cannot choose the address it is sent to without the person seeing it. |
| 109 | Tool results tell Claude that text in records is data, not instructions | Titles, notes and form leads are written by people and outsiders; a lead could contain "ignore your instructions". The server cannot stop a model from reading it, but it can say so up front and the changing tools need a connection that was allowed to write. |
| 110 | A person's time zone only changes how instants are drawn and typed; events, deadlines and API payloads stay UTC | Colleagues in different zones must see the same meeting at their own hour, and the API, MCP tools and Google sync already agree on UTC. A zone stored per event would make every consumer guess. |
| 111 | Dates without a time (deadlines, milestones, deal dates, all-day events) are not shifted by the zone | "Due 3 November" means that date for everyone; shifting it by the zone would move a deadline to the day before for people west of UTC. |
| 112 | The zone is picked in Settings → Account, with a one-time offer to use the device's zone for people still on the UTC default | An explicit choice per person was asked for; the offer removes the need to find the setting, and "Keep UTC" remembers the refusal on that device only. |
| 113 | Imports write new records in batches and a test counts the database calls | What breaks on a hosted database is the number of round trips, not the amount of data: 325 people took ~1300 sequential calls and ran into the host's time limit. A test that fails when the count grows again guards it better than a timing, which a fast local database would never trip. |
| 114 | A planned call or meeting is a CRM activity with a length, not a project event | Events live inside projects; a call with a client belongs to the contact, shows in My day and the activity timeline, and counts as a touch when done. The calendar already reads CRM activities, so it appears there without a second copy to keep in sync. |
| 115 | A planned activity is always created open, even if its minute has just passed | The default rule marks anything due in the past as done; someone scheduling for "now" or a little earlier still means to do it. |
| 116 | Efficiency is done of planned; productivity is everything finished today (planned or from the backlog) of everything that wanted attention (plan plus backlog, open or cleared) | Two different questions: "did I keep to the day's plan?" and "how much did I move, old debts included?". Both are whole percents from counts the person can see, so they can be checked by hand; with nothing planned they show a dash, never a fake 0 or 100. |
| 117 | A meeting counts as held once it has ended; a call or a follow-up counts as done only when someone marks it done | Events have no completion, but a call is something a person did or did not do. Treating an unmarked call as done would flatter the day. |
| 118 | A press on a My day card shows its own list instead of leaving the page; every list then links to its section | The list is the answer to "what is it?", the section is for working on it. Leaving at once would lose the overview. |
| 119 | A list of tasks is typed as lines, with subtasks by indent or dash, not built with a row-by-row form | The common case is pasting or typing a list from a meeting; an outline is the fastest thing to type and is understood without explanation. A preview shows what will be made. |
| 120 | Tasks are created in one batch by a dedicated service, not by calling the single-node creation in a loop | The same lesson as the import: one-by-one creation is several round trips per node, which a remote database turns into a timeout. The batch does the same checks and writes the same history once. |
| 121 | One level of subtasks: anything nested deeper in the typed list becomes a subtask of the same task | The tree allows task → subtask only; flattening is kinder than refusing a list. |
| 122 | The funnel stage is a fixed list on the contact, not the sales-pipeline stage of a deal | A person is in a relationship long before any deal exists; MLM work is about people, not offers. Deals and the pipeline stay for money. |
| 123 | The "type" letter is stored as typed and the sponsor as a name for now | The meaning of the letters is not settled yet and partners may or may not have accounts; free text loses nothing and can be turned into links in the partners step. |
| 124 | A name already in the funnel is skipped on bulk add, not merged | Typing the same list twice must not double it; merging would silently overwrite what the person already knows. |
| 125 | A person is in one group, not many | The groups split a list into lots to work or hand over; a person in two lots would be worked twice and could not be handed over cleanly. Labels that overlap are what tags are for. |
| 126 | Groups nest three levels deep and a filter on a group includes its subgroups | Deeper trees are hard to see in a side list; people think "all of the cold market" as well as "the gym". |
| 127 | Deleting a group moves its people and subgroups up instead of deleting them | A group is a way of sorting, not the person; losing the people because a folder was tidied would be the worst surprise. |
